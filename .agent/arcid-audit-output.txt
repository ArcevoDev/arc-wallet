Tech stack: Fastify + Prisma + Next.js 16 + PostgreSQL + Redis (Upstash).

3. MODULE BREAKDOWN & WALLET-RELEVANT API
------------------------------------------

3a. SDK LAYER (src/sdk/) — What ArcWallet Would Consume

The SDK is a factory-pattern pure fetch wrapper with zero framework deps.
It's designed to be extracted as a standalone npm package.

Files:
  client.ts         — Core HTTP client with 401 auto-refresh, typed ApiResponse<T>
  index.ts          — Factory singleton wiring (auth, credentials, identity, etc.)
  auth.sdk.ts       — login, register, logout, me, refresh, sessions, MFA, passkey, step-up
  credentials.sdk.ts — list, verify, issue, offer, revoke credentials
  identity.sdk.ts   — list/get identities, suspend, reinstate
  passkey.sdk.ts    — WebAuthn passkey CRUD + registration/authentication options
  oauth.sdk.ts      — OAuth clients + tokens
  tenant.sdk.ts     — tenant CRUD + switch-context
  billing.sdk.ts    — get subscription
  audit.sdk.ts      — list audit logs
  webhooks.sdk.ts   — webhook endpoint CRUD + test

3b. WALLET-SPECIFIC ENDPOINTS (Already Built)

1. register-wallet-did.flow.ts — Identity-owned did:key registration
   - POST /identity/wallet/did
   - Input: publicKeyJwk (JWK), provider, providerWalletId
   - Output: did, didDocument, walletId, keyType
   - Flow: ArcWallet generates keypair on-device → sends only public key → ArcID encodes
     as did:key, builds DID document, creates DecentralizedIdentifier + Wallet rows in 1 tx
   - Non-custodial by design: private keys never touch ArcID

2. Credential Offers (offer-credential.flow.ts)
   - POST /credentials/offers
   - Tenant creates offer → subject accepts → receives credential

3. Presentation Endpoint
   - POST /verify/session — create challenge
   - POST /verify/present — JWS-signed proof + credential presentation
   - Anti-replay: single-use sessions, 5-min TTL

4. Wallet model (Prisma)
   - Fields: id, identityId, provider, providerWalletId, createdAt
   - Unique constraint: [provider, providerWalletId]
   - Indexed by identityId

3c. PRISMA MODELS RELEVANT TO ARC-WALLET

Identity          — Core user record (primaryEmail, name, status, etc.)
DecentralizedIdentifier — did:key records owned by identity or tenant
Wallet            — Wallet binding (provider + providerWalletId)
VerifiableCredential — W3C VCs held by identity
CredentialOffer   — Pending offers for credential issuance
VerifySession     — Presentation verification challenge sessions
Session           — Auth sessions with AAL levels
Passkey           — WebAuthn passkeys
Device            — Known devices
Mfa               — TOTP/email/SMS MFA settings
ExternalIdentifier — Self-reported linked identifiers (phone, NIN, BVN, etc.)

7. INTEGRATION STRATEGY
-----------------------

OPTION A (RECOMMENDED): Consume arc-id via its HTTP API + SDK
  - ArcWallet uses the fetch-based SDK client directly
  - No tight coupling — arc-id is a standalone service
  - ArcWallet ships with its own copy of the SDK or depends on @arcid/sdk npm package
  - Authentication: OAuth 2.0 authorization code + PKCE flow
  - Credential operations: REST API calls to arc-id
  - DID management: keypair generated on-device, only public key sent to arc-id
  - This is the designed architecture — arc-id never custodies wallet private keys

OPTION B: Embed SDK as local package
  - Copy/fork the SDK into arc-wallet's codebase
  - Useful if we need to modify SDK behavior per-wallet
  - Risk of drift from arc-id's SDK

RECOMMENDATION: Start with Option A — consume arc-id staging instance via HTTP.
The SDK client.ts is 80 lines and has zero framework deps. Perfect for RN.
